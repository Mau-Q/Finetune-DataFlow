# G01/G02 共同预热数值差异：定位与修复

实验标识：20261023。状态：**G01_G02_NUMERICAL_WARMUP_RESOLVED**。结论限当前 node01 / GPU 2 软件栈、3 个独立真实 CLI 进程的 4 步共同预热；没有宣称完整 24 步策略训练、选择评分或模型评测已通过。

## 根因与证据

原数值协议固定了 PyTorch / cuBLAS / SDPA，却没有固定 FLA/Triton 的自动调优配置。实际 Qwen3.5 线性注意力走 FLA 0.4.2；Triton 3.2.0 在当前安装中不支持 `cache_results`，FLA 的 `SUPPORTS_AUTOTUNE_CACHE=False`。新进程会独立测速选配置。不同分块和 warp 配置可能采用不同浮点计算路径，即使输入、参数和 RNG 相同，也不能由种子或 math SDPA 设置保证跨进程一致。

证据来自实际运行，而非只依据源码推断：

1. G01 自身重复与 G01/G02 对照均出现差异。完整首微批输入、初始参数/量化状态/缓冲区的 3,049 项哈希，以及模块训练状态一致。G01 自身重复首微批 loss 为 4.63259363 / 4.61825132，代表性 B 梯度相对 L2 差异约 5.39%；说明问题并非只在跨策略比较中出现。
2. 逐层追踪把首次前向差异缩小到第 0 层线性注意力。保存实际完整 q/k/v/g/beta 输入后，脱离 9B 模型在独立进程重放。前 7 个阶段的输入输出一致，`chunk_fwd_o` 在完整输入一致时产生不同输出。
3. 固定 `chunk_fwd_kernel_o` 的 BK/BV=64 和 128，分别精确重现旧的两种输出哈希 `ac0247b4…` 与 `73b8f5f7…`。每个配置进程内重复 4 次都一致；BK/BV=32 产生第三种输出。
4. 只固定 chunk-o 后，差异移到融合门控归一化。对捕获的完整归一化输入做 9 种配置、每种 2 次重放，得到 2 种不同输出，每种配置自身重复一致。
5. 再固定归一化前向/反向后，G01 自身重复通过，但 G01/G02 对照仍未通过：首微批完整逐层前向一致，反向梯度已不同，第一次更新后的 loss 开始分歧。因此没有把一次自身重复成功当作完整修复。

前向配置敏感点已通过受控重放分别确认；残余反向问题没有唯一归结到某一个 kernel 的 bug。最终结论是：原执行协议遗漏了 FLA 配置选择这一数值控制变量。

## 修复

保留 `torch-math-cublas4096-v2`，增加任务进程内的 `fla-compile-ordered-config-v3`：

- chunk-o 固定 BK/BV=64、4 warps、3 stages；融合门控归一化前向/反向固定 BT=16、4 warps、2 stages。
- 其余 FLA 自动调优器按声明顺序选择可编译配置，以 compile-only 检查跳过不支持的候选，不再按每个进程的测速结果排序。
- 仅在本次任务进程内替换 FLA 配置选择逻辑；其他库的调优器保持原行为。FLA 数学实现与已安装包文件未修改，没有直接编辑已有磁盘缓存；正常 JIT 编译仍可生成缓存。
- 检查 Triton 调优器及已固定 kernel 的源码 SHA-256；来源不匹配时拒绝直接套用。保留 BF16/NF4、LoRA dropout=0.05、共享初始 adapter、微批种子和原审计容差。

独立算子前向/反向 smoke 完成 142 项候选编译检查，未遇到不支持的候选，梯度有限。修复实现见 `fla_numerical_policy.py`、`fla_compile_policy.py` 和 `probe_fixed_preselection_v3.py`。它是已验证的实验执行控制，还未接入整组正式训练控制器。
