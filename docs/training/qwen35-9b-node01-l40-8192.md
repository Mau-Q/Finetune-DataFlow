## 1. 本次要完成什么

- 模型固定为官方 `Qwen/Qwen3.5-9B`，revision `c202236235762e1c871ad0ccb60c8ee5ba337b9a`。

- 再用有效长度接近 4096、8192 的构造数据测显存；单独记录成功、OOM 或其他错误。短训跑通与 8192 容量分别报告。

## 4. Mac 下载、学校离线安装

学校服务器按离线环境处理，不要求它访问 PyPI、GitHub 或 Hugging Face，也不建立临时联网转发。

1. 在 Mac 下载 Linux x86_64／CPython3.12 依赖；复用基础镜像已满足的版本。DataFlex 和固定 LLaMA-Factory 从原样源码构建纯 Python wheel。

3. 上传到 node01，核验服务器文件完整后，删除 Mac 本轮下载的临时权重、依赖包和传输压缩包；失败文件保留以便重试。保留小型清单、脚本和日志。
4. 新训练容器使用 `pip --no-index --find-links` 安装；将模型目录只读挂载。移除这个新容器继承的旧 vLLM、句向量、云存储/遥测组件，避免无关包约束污染训练环境。causal-conv1d 在容器内使用现有 CUDA12.4 编译器离线构建。记录 pip check、实际包版本和试训结果。

不改动已有推理/MinerU 容器、宿主 Conda、驱动或其他用户任务。新训练进程单独限制显存使用，运行前刷新 GPU 占用；不能把过去的空闲快照当成当前分配。

## 8. 输入长度上限测试

[capacity-sweep.py](../../deploy/plans/qwen35-9b-8192/capacity-sweep.py) 在基础试训结束后运行。每轮使用新进程、独立输出目录、两次 optimizer update，固定 NF4 QLoRA、BF16、SDPA、gradient checkpointing、micro batch 1、LoRA r=16，先从 8192 倍增，再以 1024 token 精度缩小通过/OOM 区间。只有实际 CUDA OOM 计入上界；编译、数据或其他错误单独停止。

GPU 3 上已有约 9.6 GiB 的其他任务占用。测试的 PyTorch 分配预算固定为启动时空闲显存减去 3 GiB，并限制在 PyTorch 可见总显存的 80% 以内；每轮检查空闲显存，发现新的占用便停止。3 GiB 是分配器外预算，CUDA 运行库也会消耗其中一部分，并非整卡始终保留 3 GiB。记录的是此共享 GPU 和此显存预算下的上限，不能称作整卡独占极限。构造样本答案为 5 个监督 token，容量结果也不能代替正式数据长答案训练的验证。结果写入服务器 `runs/qwen35-9b/20261022-smoke/capacity-sweep/report.json`。

实测配置：node01 GPU 3，NF4 QLoRA、BF16、SDPA、gradient checkpointing、LoRA r=16、微批 1、梯度累积 1；每个通过档位均完成两次 optimizer update，loss 和保存的 adapter 权重有限，248 个 LoRA B 张量非零。GPU 既有任务保持运行。

| 实际有效 token | 结果 | PyTorch 峰值 allocated / reserved | 分配器 |
| ---: | --- | --- | --- |
| 512 | 通过，另有 adapter 重载/生成通过 | 9.63 / 10.46 GiB | 默认，26.59 GiB 限额 |
| 4096 | 通过 | 20.52 / 23.42 GiB | 默认，26.59 GiB 限额 |
| 6144 | 通过 | 26.75 / 31.00 GiB | 默认，31.30 GiB 限额 |
| 7168 | 默认分配器第二步 OOM；优化后通过 | 29.86 / 30.29 GiB（通过轮） | expandable_segments:True，31.30 GiB 限额 |
| 8192 | 默认与优化分配器均 OOM | 在反向传播申请额外约 7.65 GiB 时失败 | 优化轮仍为 31.30 GiB 限额 |

最终共享 GPU 的通过/OOM 区间为 **7168～8192 token，精度 1024**；没有逐 token 测出精确阈值。`run-smoke.sh` 和后续容量脚本默认使用 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，DataFlex 源码与依赖声明保持不变。当前共享卡常规训练先用 6144，7168 属于本轮已通过的短测上沿。

### 独占整卡估计（未执行）

驱动显示整卡总量 44.99 GiB，其中保留 696 MiB；CUDA 可分配总量约 **44.31 GiB**。四个通过档位的 allocated 峰值近似为 `8.07 + 0.00304 × token数` GiB。优化后的 7168 轮，驱动两秒采样峰值扣除原有任务约 32.76 GiB，比 allocated 高约 2.90 GiB。此采样只是近似值，不能捕获所有瞬时峰值；按该额外开销估算，并另留 1～2 GiB 余量：

| 独占输入长度 | 估计训练进程显存（含上述额外开销） | 判断 |
| ---: | ---: | --- |
| 8192 | 约 35.9 GiB | 适合作为独占后的首个实测档位 |
| 10240 | 约 42.1 GiB | 接近边缘，可作为下一档测试 |
| 11264 | 约 45.2 GiB | 可能超过可分配总量 |
| 16384 | 约 60.8 GiB | 当前配置预计不可行 |

因此独占整卡时估计约 **1 万 token** 可用，贴边极限约 **1.1 万 token**；实际训练建议先用 8192。以上是超出通过档位的外推，未停止其他任务做独占测试。正式数据、长时间训练、不同微批/LoRA/内核形状都可能改变结果，不能把估计值标为实测通过。
